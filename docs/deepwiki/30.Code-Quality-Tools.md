This document describes the code quality tools configured for the CopySVGTranslation project, including code formatters, linters, and their integration with the development workflow. These tools enforce consistent code style, catch potential issues, and ensure code quality standards are maintained across the codebase.

For information about running tests, see [Testing](/MrIbrahem/CopySVGTranslation/7.2-testing). For CI/CD workflow execution, see [CI/CD Workflows](/MrIbrahem/CopySVGTranslation/7.4-cicd-workflows).

## Linting Tools

### Pylint Configuration

Pylint performs static code analysis and enforces coding standards:

```

```

**Key Settings:**

| Setting | Value | Rationale |
| --- | --- | --- |
| `ignore` | `venv,tests` | Excludes virtual environment and test directories |
| `extension-pkg-whitelist` | `lxml` | Prevents false positives for `lxml` C extension |
| `max-line-length` | `100` | Matches Black and isort |
| Disabled checks | docstring and class checks | Reduces noise for technical documentation |

**Disabled Checks:**

* `missing-module-docstring`: Module-level docstrings not required
* `missing-class-docstring`: Class-level docstrings not required
* `missing-function-docstring`: Function-level docstrings not required
* `too-few-public-methods`: Allows simple data classes and exceptions

The `lxml` whitelist is critical because `lxml` uses C extensions that Pylint cannot introspect, which would otherwise generate false positive errors for valid `lxml` usage throughout the codebase (e.g., `etree.Element`, `etree.parse`).

### Flake8 Configuration

Flake8 enforces PEP 8 style guidelines with Black-compatible adjustments:

```

```

**Key Settings:**

| Setting | Value | Rationale |
| --- | --- | --- |
| `max-line-length` | `100` | Matches Black, isort, and pylint |
| `extend-ignore` | `E203, W503` | Black compatibility |
| `per-file-ignores` | `src/app.py:E402` | File-specific exceptions |

**Ignored Warnings:**

* **E203** (whitespace before ':'): Black sometimes adds whitespace that violates this rule in slice notation
* **W503** (line break before binary operator): Conflicts with modern style (W504 is the preferred style, but Black handles this)

The `per-file-ignores` entry for `src/app.py:E402` appears to be legacy configuration, as this file does not exist in the current project structure.

## Test Configuration

### Pytest Settings

Pytest is configured with markers, test discovery patterns, and execution options:

```

```

**Test Discovery:**

* **Test Directory**: `tests/`
* **Test Files**: Match `test*.py` or `*Test.py`
* **Test Classes**: Start with `Test`
* **Test Functions**: Start with `test`

**Default Options** (`addopts`):

* `-vv`: Very verbose output showing individual test names
* `--tb=short`: Shorter traceback format
* `--strict-markers`: Fail on undefined markers
* `-m "not todo"`: Exclude tests marked with `@pytest.mark.todo` by default

**Test Markers:**
The configuration defines six custom markers for categorizing tests:

| Marker | Purpose | Example Usage |
| --- | --- | --- |
| `slow` | Long-running tests | `pytest -m "not slow"` |
| `integration` | Multi-module tests | `pytest -m integration` |
| `unit` | Single-module tests | `pytest -m unit` |
| `auth_required` | Needs credentials | Skip in CI if no auth |
| `network` | Requires internet | Skip in offline environments |
| `todo` | Not yet implemented | Excluded by default |

The `todo` marker is used in [tests/nested_analyze/test_fix_nested_file_new.py L84](https://github.com/MrIbrahem/CopySVGTranslation/blob/307ef348/tests/nested_analyze/test_fix_nested_file_new.py#L84-L84)

 to mark incomplete test cases that represent future functionality.

**Warning Filters:**
Both `DeprecationWarning` and `PendingDeprecationWarning` are suppressed to reduce noise from dependencies (primarily from `lxml`).

## Code Quality Tool Chain

```

```

**Recommended Workflow:**

1. **Write/Modify Code**: Make changes to Python files
2. **Format**: Run `isort` first, then `black` (order matters for import formatting)
3. **Lint**: Run `pylint` and `flake8` to catch style issues and potential bugs
4. **Test**: Run `pytest` to verify functionality
5. **Commit**: Commit changes after all checks pass

The tools are currently not enforced automatically, so developers must run them manually before committing.

## CI/CD Integration

Currently, only pytest is integrated into the CI/CD pipeline. The GitHub Actions workflow runs tests on all pull requests:

```

```

**Workflow Behavior:**

* **Trigger**: All pull requests to any branch
* **Python Version**: 3.10 (minimum supported version)
* **Dependencies**: Installs `pytest` and runtime dependencies from `requirements.txt`
* **Test Command**: Runs `pytest` with default options from [pytest.ini L6](https://github.com/MrIbrahem/CopySVGTranslation/blob/307ef348/pytest.ini#L6-L6)  (excludes `todo` tests)

**Not Automated:**
The following tools are **not** run in CI/CD:

* `black` (code formatting verification)
* `isort` (import organization verification)
* `pylint` (static analysis)
* `flake8` (style checking)

This means code formatting and linting are developer responsibilities and are not enforced on pull requests. The project could benefit from adding these checks to CI/CD to ensure consistent code quality.

## Configuration Summary

**Consistency Across Tools:**

All tools share a common line length of 100 characters:

| Tool | Configuration Key | Value |
| --- | --- | --- |
| black | `line-length` | 100 |
| isort | `line_length` | 100 |
| pylint | `max-line-length` | 100 |
| flake8 | `max-line-length` | 100 |

**Python Version Targets:**

* **black**: Targets Python 3.11 syntax
* **Project**: Requires Python 3.10+ ([pyproject.toml L10](https://github.com/MrIbrahem/CopySVGTranslation/blob/307ef348/pyproject.toml#L10-L10) )
* **CI/CD**: Tests on Python 3.10

**Tool Compatibility:**

* **isort**: Uses `profile = "black"` for automatic Black compatibility
* **flake8**: Ignores `E203` and `W503` which conflict with Black
* **pylint**: Whitelists `lxml` extension to prevent false positives
